# Установка синхронизации продаж и возвратов в расширение 1С

## Состав расширения

Все объекты создаются в существующем расширении/агенте dh-carpet. Конфигурация поставщика не редактируется.

Создайте пять неглобальных общих модулей со следующими именами и вставьте указанные исходники:

| Имя общего модуля | Исходник |
|---|---|
| `ДХКоверПродажиСервер` | `integrations/1c/SalesAdapter.bsl` |
| `ДХКоверВозвратыСервер` | `integrations/1c/CustomerReturnsAdapter.bsl` |
| `ДХКоверТранспортСервер` | `integrations/1c/Transport.bsl` |
| `ДХКоверНастройкиСервер` | `integrations/1c/ProtectedSettings.bsl` |
| `ДХКоверСобытияСервер` | `integrations/1c/DocumentEventHandlers.bsl` |

Для каждого из пяти модулей установите одинаковые свойства:

- `Глобальный` — Нет;
- `Клиент (управляемое приложение)` — Нет;
- `Клиент (обычное приложение)` — Нет, если это свойство показывается;
- `Сервер` — Да;
- `Вызов сервера` — Нет;
- `Внешнее соединение` — Да;
- `Привилегированный` — Нет;
- `Повторное использование` — Не использовать.

`Вызов сервера` не нужен: подписки и все вызываемые ими модули выполняются на сервере. API key извлекается только на сервере из общего безопасного хранилища БСП с владельцем `dh-carpet.integration` и ключом `КлючAPI`.

До включения подписок существующая административная форма настроек агента должна один раз вызвать на сервере:

```bsl
ДХКоверНастройкиСервер.СохранитьПараметрыПодключения(АдресСервера, КлючAPI);
```

Поле формы `КлючAPI` должно иметь `РежимПароля = Да`, не быть сохраняемым реквизитом формы и очищаться сразу после серверного вызова. Реальный ключ нельзя вставлять в модуль, макет, константу или Git. Используйте уже настроенный HTTPS-адрес внутреннего API; адрес нельзя угадывать по `127.0.0.1`, поскольку он зависит от сетевого маршрута сервера 1С до reverse proxy dh-carpet.

## Подписки на события

В основное дерево расширения заимствуйте без изменения модулей два объекта поставщика:

- `Документы → РасходнаяНакладная`;
- `Документы → ПриходнаяНакладная`.

Создайте в `Общие → Подписки на события` две подписки:

| Имя подписки | Источник | Событие | Обработчик |
|---|---|---|---|
| `ДХКоверРасходнаяНакладнаяПослеЗаписи` | `ДокументОбъект.РасходнаяНакладная` | `ПриЗаписи` | `ДХКоверСобытияСервер.РасходнаяНакладнаяПослеЗаписи` |
| `ДХКоверПриходнаяНакладнаяПослеЗаписи` | `ДокументОбъект.ПриходнаяНакладная` | `ПриЗаписи` | `ДХКоверСобытияСервер.ПриходнаяНакладнаяПослеЗаписи` |

Отдельные подписки для проведения и распроведения не создаются. `ПриЗаписи` вызывается при обычной записи, проведении, перепроведении, распроведении и сохранении изменённой табличной части. Адаптер каждый раз формирует полный актуальный snapshot непосредственно из объекта `Источник`; повторного чтения документа из базы по ссылке нет. Для распроведённого документа или документа другого вида операции отправляется пустой snapshot с `posted=false`.

Имена подписок и процедур с фрагментом `ПослеЗаписи` сохранены только ради совместимости с уже подготовленным расширением; фактическое событие обеих подписок — `ПриЗаписи`, а сигнатура каждого обработчика содержит параметры `(Источник, Отказ)`.

Обработчики не устанавливают `Отказ`, не показывают сообщения пользователю и перехватывают все исключения настроек, запросов 1С, HTTPS и API. Ошибка записывается в журнал регистрации как `dh-carpet.Синхронизация1С`; даже сбой самого журнала не выходит из обработчика. HTTP timeout равен 10 секундам.

## Точные действия в Конфигураторе

1. Запустите Конфигуратор и откройте рабочую информационную базу.
2. Выберите `Конфигурация → Расширения конфигурации` и откройте существующее расширение/агент dh-carpet.
3. В дереве основной конфигурации найдите `Документы → РасходнаяНакладная`, вызовите контекстное меню и нажмите `Добавить в расширение`.
4. Аналогично добавьте `Документы → ПриходнаяНакладная`. Их модули и реквизиты не изменяйте.
5. В дереве расширения откройте `Общие → Общие модули`, нажмите `Добавить` и последовательно создайте пять модулей из таблицы выше.
6. Для каждого модуля выставьте свойства из списка выше, откройте `Модуль` и целиком вставьте содержимое соответствующего `.bsl`-файла.
7. В дереве расширения откройте `Общие → Подписки на события`, нажмите `Добавить`.
8. Укажите имя `ДХКоверРасходнаяНакладнаяПослеЗаписи`.
9. В поле `Источник` нажмите кнопку выбора и отметьте только `ДокументОбъект.РасходнаяНакладная`.
10. В поле `Событие` выберите `ПриЗаписи`.
11. В поле `Обработчик` выберите `ДХКоверСобытияСервер.РасходнаяНакладнаяПослеЗаписи`.
12. Создайте вторую подписку с именем `ДХКоверПриходнаяНакладнаяПослеЗаписи`.
13. Для неё выберите источник `ДокументОбъект.ПриходнаяНакладная`, событие `ПриЗаписи`, обработчик `ДХКоверСобытияСервер.ПриходнаяНакладнаяПослеЗаписи`.
14. Выполните `Конфигурация → Проверка конфигурации`; устраните ошибки до обновления базы.
15. Сохраните расширение и выполните `Конфигурация → Обновить конфигурацию базы данных` только для расширения.
16. До начала проверки сохраните HTTPS-адрес и production API key через существующую защищённую форму настроек агента. Не вводите ключ в исходный код или консоль запросов.

## Ручная проверка

Используйте согласованный тестовый документ/контрагента, чтобы не исказить реальный учёт.

### Продажа

1. Создайте или выберите тестовую `Расходную накладную` с `ВидОперации = Продажа покупателю` и одной строкой `Запасы`, номенклатура которой уже существует в dh-carpet по штрихкоду.
2. Запишите и проведите документ.
3. Найдите ковёр по barcode через `GET /api/rugs/by-barcode/{barcode}`, затем запросите `GET /api/rugs/{rug_id}/history?event_type=sale&page_size=200` с защищённым заголовком `X-Internal-API-Key`.
4. Зафиксируйте `id`, `source_ref`, цену и количество появившегося sale event.
5. Измените цену или количество той же строки и перепроведите документ.
6. Повторите запрос: `id` и `source_ref` должны остаться прежними, цена/количество должны обновиться, второй event для того же `source_ref` и line key появиться не должен.
7. Распроведите документ и повторите запрос. Событие с этим `source_ref` должно исчезнуть из видимой истории.

### Возврат

1. Создайте или выберите тестовую `Приходную накладную` с `ВидОперации = Возврат от покупателя` и одной строкой `Запасы`.
2. Проведите документ и запросите историю с `event_type=customer_return`.
3. Убедитесь, что появился один event с правильными barcode, ценой, количеством, единицей и контрагентом.
4. Измените цену или количество, перепроведите и убедитесь, что обновилась та же запись без дубля.
5. Распроведите документ и убедитесь, что событие исчезло из видимой истории.

При сетевой ошибке документ должен записаться/провестись, а в журнале регистрации должна появиться запись события `dh-carpet.Синхронизация1С`. Автоматической очереди повторов на этом этапе нет: после восстановления связи документ нужно записать или перепровести повторно.
