# Этап 3: 1С, история и фотоархив

## Подтверждённые данные 1С

Импорт охватывает все товары (включая нулевой остаток и ранее проданные) из корневых групп `Ковры`, `Ковролины`, `Ковролины (в т.ч. дорожки)`, `Шкуры` и всех подгрупп. Группы и помеченная на удаление номенклатура исключаются. Категории API: `rug`, `carpet`, `hide`.

Подтверждён `Справочник.Номенклатура` и поля `Наименование`, `Артикул`, `Штрихкод`, `Длина`, `Ширина`, `Вес`, `Описание`, `Комментарий`, `ПометкаУдаления`. Описание выбирается с fallback на комментарий. Barcode — business ID; уникальный article индексируется. В целевой архитектуре остаток поступает из виртуальной таблицы остатков `РегистрНакопления.Запасы` и хранится отдельно: ноль не означает продажу и не меняет status. Точные измерения и ресурсы реального регистра должны быть подтверждены результатом `CatalogMetadataDiscovery.bsl` до реализации BSL-адаптера.

Из `РегистрСведений.ЦеныНоменклатуры` принимается только вид цен с наименованием `Розничная цена`. Текущее значение хранится в карточке, реальные изменения — структурированными событиями `retail_price_change`; повтор одинакового значения событие не создаёт. Для ковролина сохраняется единица цены. Точные имена измерений и ресурсов реального регистра цен пока не подтверждены и не подставляются предположительно.

Дополнительные реквизиты ищутся в 1С сначала по identifier, затем по имени. Нормализованные значения (`pile_height_mm`, `density_mln_m2`, `production_method`, `patterns`, `styles`, `colors`, `materials`, `rug_base`, `pile_composition`, `origin_country`, `brand_country`, `ornaments`, `pile_type`, `features`, `room`, `collection`, `shape`, `anti_slip`, `extra_elements`) сохраняются в JSONB `attributes`, вес — в `weight_kg`.

## Locations и фотографии

Каждый полный snapshot содержит все склады и ячейки. Неизменные записи переиспользуются по fingerprint, новые открываются, исчезнувшие закрываются через `is_current=false` и `valid_to`; история не удаляется. Фотографии карточки 1С обрабатываются только для `jpg/jpeg/png/webp/heic`, сравниваются по external id/checksum/fingerprint и также сохраняют историю.

Внешний архив `D:\Фото ковров\` монтируется в Ubuntu по SMB read-only, целиком не копируется. Команда `python -m app.cli scan-photo-archive --root <mount>` рекурсивно индексирует файлы `АРТИКУЛ.ext` и `АРТИКУЛ_ЧИСЛО.ext`, считает SHA-256, читает размеры при поддержке Pillow и сопоставляет только точный article. Повторный checksum одного ковра не создаёт дубль. Проверка доступности mount выполняется до изменения БД; недоступность SMB не закрывает существующий индекс.

## События и синхронизация

`rug_events` хранит `retail_price_change`, `sale`, `customer_return`, `lalita_price`. Продажи и возвраты имеют стабильную пару source document/line key; изменение обновляет запись, распроведение делает её невидимой. Возврат принимается только после отбора в 1С проведённых `Приходных накладных` с операцией `Возврат от покупателя`. Номер документа технический и отсутствует в обычном response.

`POST /api/internal/1c/bulk` поддерживает initial/incremental пакеты, sync runs, per-item result, идемпотентность и повтор после сетевой ошибки. Для продажи и возврата вместе с событиями передаётся `document_snapshots`: тип события, UUID документа, признак проведения и полный набор `ИдентификаторСтроки`. Backend обновляет существующие строки и скрывает отсутствующие; пустой snapshot с `posted=false` скрывает все события распроведённого документа. Если импорт хотя бы одной строки документа завершился ошибкой, reconciliation его snapshot не выполняется.

Internal API отделён от защищённых административных Lalita endpoints. История, recent history, locations, photo sources и price graph защищены server-side ключом до появления пользовательской auth-модели.

## Lalita и график

Lalita event создаётся `pending_confirmation`; администратор dh-carpet исправляет ту же запись и переводит её в `confirmed` либо отклоняет с физическим удалением бизнес-события (audit операции сохраняется). Новое предложение из другого видео заменяет прошлое (`replaced`). Expiration вычисляется отдельно от status, поэтому pending и expired совместимы. Процентная/абсолютная скидка фиксирует розничную цену на дату видео и рассчитанную цену; `up_to_percent` автоматически не рассчитывается.

Graph API по умолчанию возвращает год и семантические серии `retail_price`, `lalita_price`, `sale_price`; возвраты исключены, цвета не задаются. Recent API возвращает максимум 20 видимых событий, исключая expired/replaced Lalita; полная история поддерживает период, типы и состояния.

## Права и metadata discovery

Расширение 1С должно иметь отдельное право просмотра блока и графика; без него код формы не вызывает backend. Те же данные закрыты на API. Pending виден пользователям с правом просмотра, но подтверждение из 1С отсутствует.

Metadata discovery завершён на реальной базе 1С. Продажа читается из проведённого `Документ.РасходнаяНакладная`, табличной части `Запасы`, только при `ВидОперации = Перечисления.ВидыОперацийРасходнаяНакладная.ПродажаПокупателю`. Возврат читается из проведённого `Документ.ПриходнаяНакладная`, табличной части `Запасы`, только при `ВидОперации = Перечисления.ВидыОперацийПриходнаяНакладная.ВозвратОтПокупателя`.

В обоих документах используются реквизит `Контрагент` и поля строки `Номенклатура`, `Цена`, `Количество`, `ЕдиницаИзмерения`, `ИдентификаторСтроки`. Стабильный document key — `Ссылка.УникальныйИдентификатор()`, стабильный line key — `ИдентификаторСтроки`; `НомерСтроки` не используется. Подтверждённый контракт зафиксирован в `integrations/1c/tests/confirmed-metadata.json` и проверяется статическими тестами адаптеров.
